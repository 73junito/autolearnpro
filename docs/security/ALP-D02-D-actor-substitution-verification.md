## Objective

Confirm that a restricted approval database connection cannot submit a role request on behalf of a different actor by supplying an arbitrary requester UUID. This tests the database trust boundary, **not** just the HTTP handler.

## Implemented test

The existing `tests/approval-executor-live.test.mjs` test uses a scratch-only loopback URL, an expected migration count, and a random marker generated by the disposable CI harness before fixture writes.

After its synthetic auth users are created, D02-D now:
1. Obtains the restricted `alp_approval_ci_login` connection.
2. Starts a transaction and selects `alp_approval_executor`.
3. Calls `alp_private.submit_role_request` with the UUID of a separate synthetic actor.
4. **Expects rejection** by the database privileged function.
5. Rolls back the transaction in all cases.

The test is deliberately strict. **As currently designed, the `SECURITY DEFINER` function accepts a caller-supplied requester UUID and may allow this call.** A failing negative control demonstrates that the trust boundary remains open; it is not a flaky test or permission to weaken the assertion.

## Existing controls (not sufficient for independent identity assurance)

The HTTP handler verifies bearer credentials with GoTrue and passes the resulting actor into SQL. Restricted executor roles lack `SUPERUSER` and `BYPASSRLS`; approval functions are hidden from anonymous and ordinary authenticated roles. The approval decision routine blocks self-approval and administrator elevation.

However, a connection with `EXECUTE` on a privileged function should not be treated as an independently authenticated end user. Caller-provided actor arguments and caller-editable PostgreSQL settings do not close this trust boundary.

## Remediation design gate

Before any migration, evaluate whether a carefully scoped trusted broker, independent token verifier, or a more restrictive capability model can enforce actor attribution without trusting discretionary database-session inputs. Include replay defense, audit, revocation, key handling, rollback, function ownership and least-privilege impact. A simple equality check against a client-set `request.jwt.claim.sub` is not acceptable.

When the schema is corrected in an approved disposable test environment, the D02-D negative control must pass without weakening its assertion.
